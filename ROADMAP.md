# Open Street Cat — roadmap разработки

Это инженерный backlog функций, нужных для ограниченного пилота Open Street Cat. Задачи описывают, что менять в клиенте, API и базе данных и по каким критериям принимать результат. Их можно брать в разработку по одной, соблюдая зависимости.

## Цель пилотной версии

Житель может зарегистрироваться, найти или создать карточку кота, оставить актуальное наблюдение или запрос помощи. Участник понимает статус случая и может связаться с ответственным. Координатор может поддерживать данные в актуальном состоянии и разбирать ошибки.

Текущая реализация уже содержит главную страницу, карту, просмотр и создание кота, регистрацию/вход, создание/просмотр/закрытие событий помощи, статистику и PostgreSQL/PostGIS. В задачах ниже эти функции не считаются отсутствующими; они расширяются там, где сейчас не замыкают пилотный сценарий.

## Приоритеты

- **P0** — необходимо для ограниченного пилота с реальными участниками.
- **P1** — улучшение после первого рабочего пилота.
- **P2** — масштабирование или дополнительные сценарии.

Оценки — примерный размер инженерной работы в днях, без ожидания решений партнёра и дизайна. Каждая задача предполагает обновление документации/API-типа там, где меняется контракт.

## Текущий прогресс

Проверено по коду на 20 ноября 2026 года. Создание кота, редактирование кота и страница профиля уже реализованы. Отметка «готово» означает наличие соответствующего сценария в клиенте и API; это не заменяет отдельную проверку качества/безопасности.

- [x] Создание кота: авторизованная форма на карте и `POST /api/cats`.
- [x] Редактирование кота: форма на карте, `PATCH /api/cats/:id`, проверка авторства на сервере.
- [x] Страница профиля `/profile` и публичный профиль `/users/:id`: данные пользователя, счётчики и до 10 последних действий.
- [ ] Выход из аккаунта из интерфейса: API logout есть, но кнопка в шапке ведёт на несуществующий маршрут `/logout`.
- [ ] Решение о видимости статистики и активности профиля: сейчас `GET /api/users/:id` публично отдаёт счётчики и активность.

## Этап 1. Личный кабинет и пользовательский контур

### DEV-001 — Добавить страницу личного кабинета

- **Статус:** Готово
- **Приоритет:** P0 · **Оценка:** 2–3 дня · **Зависимости:** нет
- **Реализовано:** маршрут `/profile`, страница `ProfilePage`, состояния загрузки/ошибки/пустого списка, ссылки в навигации; публичный маршрут `/users/:id`.
- **Функции:** показать имя, дату регистрации, счётчики добавленных котов/событий помощи/решённых событий и до 10 последних действий со ссылками на карточки котов.
- **Готово, когда:** авторизованный пользователь видит свой профиль; гость с `/profile` перенаправляется на `/login`; публичный `/users/:id` показывает профиль другого пользователя; интерфейс имеет загрузку, ошибку, пустое состояние и мобильную компоновку.

### DEV-002 — Реализовать API активности пользователя

- **Статус:** Готово с уточнением: активность доступна через публичный `GET /api/users/:id`, отдельного `GET /api/users/me/activity` нет.
- **Приоритет:** P0 · **Оценка:** 1–2 дня · **Зависимости:** нет
- **Реализовано:** `GET /api/users/:id` отдаёт профиль, статистику и последние действия. Для собственной страницы клиент использует этот endpoint по ID из текущего Zustand state.
- **Готово, когда:** данные выбираются по ID маршрута; endpoint отдаёт только публичный профиль, счётчики и максимум 10 последних событий; пароли и секреты не возвращаются; неизвестный ID даёт 404. Видимость этих данных должна быть явно утверждена в DEV-006.

### DEV-003 — Связать профиль с API и текущей сессией

- **Статус:** Готово для загрузки профиля; очистка кэша при выходе не реализована и вынесена в DEV-005.
- **Приоритет:** P0 · **Оценка:** 1–2 дня · **Зависимости:** DEV-001, DEV-002
- **Реализовано:** `useUser` загружает публичный профиль через `GET /api/users/:id`; `GET /api/users/me` используется для восстановления текущей сессии приложением.
- **Готово, когда:** компонент профиля загружает API по ID, показывает состояния загрузки/ошибки/пустого списка; сессию приложения и выход обрабатывают отдельные задачи DEV-005.

### DEV-004 — Уточнить страницу и состояние регистрации/входа

- **Приоритет:** P0 · **Оценка:** 1–2 дня · **Зависимости:** DEV-001
- **Изменения:** проверить, что регистрация и вход доступны из одной страницы `/login`, добавить понятные сообщения о занятом логине, слабом пароле и неверных данных; после входа вернуть пользователя в исходный закрытый сценарий, если он был.
- **Готово, когда:** ошибки API отображаются рядом с формой; пароль не попадает в URL/логи клиента; состояние пользователя после регистрации и входа обновляется без перезагрузки страницы.

### DEV-005 — Подключить выход из аккаунта в интерфейсе

- **Приоритет:** P0 · **Оценка:** 0.5–1 день · **Зависимости:** DEV-003
- **Текущее состояние:** `POST /api/auth/logout` очищает cookie, но кнопка в `Header.tsx` ведёт на `/logout`, такого маршрута нет; в профиле действие выхода отсутствует.
- **Изменения:** реализовать logout mutation и обработчик кнопки; после успешного ответа очистить Zustand user state и кэш TanStack Query; перенаправить на главную или страницу входа.
- **Готово, когда:** выход доступен на desktop и mobile; cookie очищается сервером; после выхода приватные разделы/действия закрыты, данные предыдущего пользователя не видны; ошибка выхода показана пользователю.

### DEV-006 — Зафиксировать и реализовать видимость профилей

- **Приоритет:** P0 · **Оценка:** 1–2 дня · **Зависимости:** нет
- **Текущее состояние:** `GET /api/users/:id` публично отдаёт имя, дату регистрации, агрегированные счётчики и до 10 последних действий. Профиль содержит ссылки на котов, созданные пользователем.
- **Изменения:** выбрать для пилота одно из правил: оставить эти данные публичными, скрыть активность за авторизацией или показывать только агрегаты; затем применить правило в API и интерфейсе и указать его на странице профиля.
- **Готово, когда:** неавторизованный и авторизованный доступ ведут себя по одному документированному правилу; API не отдаёт скрытые поля; профиль отражает выбранный уровень видимости.

## Этап 2. Карточки, наблюдения и фотографии

### DEV-009 — Реализовать создание карточки кота

- **Статус:** Готово: авторизованная форма карты отправляет координаты, имя, пол и описание на `POST /api/cats`; API сохраняет создателя и координаты в PostGIS.
- **Приоритет:** P0 · **Оценка:** выполнено · **Зависимости:** нет
- **Готово, когда:** кот создаётся авторизованным пользователем; без имени сервер назначает имя; созданная карточка открывается после сохранения.

### DEV-010 — Добавить API редактирования кота

- **Статус:** Готово: `PATCH /api/cats/:id`, Zod-схема и проверка автора реализованы.
- **Приоритет:** P0 · **Оценка:** 2–3 дня · **Зависимости:** нет
- **Реализовано:** маршрут `PATCH /api/cats/:id`, схема Zod и серверная проверка автора. Последующая работа по общим ошибкам и статусам описана в DEV-040.
- **Готово, когда:** API и клиент могут изменить разрешённые поля; доступ проверяется сервером; частичное обновление не затирает поля, которых нет в запросе; неактивный/архивный кот нельзя редактировать обычным сценарием.

### DEV-011 — Добавить интерфейс редактирования карточки кота

- **Статус:** Готово: действие доступно автору карточки, форма редактирует имя, пол, описание и точку.
- **Приоритет:** P0 · **Оценка:** 2–3 дня · **Зависимости:** DEV-010
- **Реализовано:** действие редактирования на странице кота открывает форму через режим карты; подключены mutation и обновление кэша.
- **Готово, когда:** пользователь с правом редактирования меняет имя, пол, описание и координаты; ошибки валидации отображаются; после сохранения страница и карта показывают новые данные.

### DEV-012 — Спроектировать записи наблюдений отдельно от карточки кота

- **Приоритет:** P0 · **Оценка:** 3–5 дней · **Зависимости:** нет
- **Изменения:** подготовить миграцию и контракты для сущности наблюдения: кот, автор, время, координаты/точность, описание и фото. Не мигрировать данные автоматически без проверки соответствия текущих записей.
- **Готово, когда:** модель различает идентичность кота и повторные сообщения о его местонахождении; описана миграция существующих данных и поведение API списка/карточки; клиентские типы согласованы с сервером.

### DEV-013 — Реализовать создание и просмотр наблюдений

- **Приоритет:** P0 · **Оценка:** 4–6 дней · **Зависимости:** DEV-012
- **Изменения:** добавить API создания наблюдения и список наблюдений в карточке кота; обновить форму добавления на карте, чтобы она создавала/привязывала наблюдение.
- **Готово, когда:** авторизованный пользователь может добавить наблюдение существующего кота; публичный пользователь видит историю наблюдений с датами; координаты каждого наблюдения не перезаписывают историю.

### DEV-014 — Подключить загрузку и показ фотографий

- **Приоритет:** P0 · **Оценка:** 3–5 дней · **Зависимости:** DEV-012
- **Изменения:** реализовать API загрузки/получения/удаления фото, используя `cat_photos`; подключить имеющийся Multer middleware или заменить его в соответствии с выбранным хранилищем; добавить загрузку в форму наблюдения и отображение в карточке.
- **Готово, когда:** принимаются только разрешённые форматы и размер; ошибка загрузки не оставляет битую запись; фото доступны только через контролируемый URL; пользователь с правами может удалить фото; секреты/файлы не публикуются случайно.

### DEV-015 — Добавить подтверждение актуальности записи

- **Приоритет:** P0 · **Оценка:** 2–3 дня · **Зависимости:** DEV-012
- **Изменения:** добавить событие подтверждения «кот/место всё ещё актуальны», автора и дату; отображать дату последнего подтверждения и пометку устаревшей записи.
- **Готово, когда:** повторное подтверждение добавляет историю, не меняя исходную дату наблюдения; срок актуальности настраивается константой/конфигурацией; пользователь видит, когда сведения последний раз проверялись.

## Этап 3. Жизненный цикл помощи и координация

### DEV-020 — Добавить состояния обработки запроса помощи

- **Приоритет:** P0 · **Оценка:** 3–4 дня · **Зависимости:** нет
- **Изменения:** дополнить модель `help_requests` или связанную таблицу статусами обработки (например, открыто, принято, в работе, решено, отменено), автором и временем каждого изменения.
- **Готово, когда:** текущий статус вычисляется однозначно; история переходов сохраняется отдельно/не перезаписывается; миграция сохраняет старые `needed`/`resolved` события и имеет описанный rollback или процедуру восстановления.

### DEV-021 — Реализовать принятие и назначение запроса

- **Приоритет:** P0 · **Оценка:** 2–4 дня · **Зависимости:** DEV-020, DEV-030
- **Изменения:** добавить endpoint для координатора, чтобы принять запрос и назначить ответственного; отображать назначение в карточке.
- **Готово, когда:** назначение и снятие назначения доступны только подходящей роли; пользователь видит, что случай уже взят; конкурирующие назначения не перетирают друг друга молча.

### DEV-022 — Добавить интерфейс обработки запроса помощи

- **Приоритет:** P0 · **Оценка:** 3–4 дня · **Зависимости:** DEV-020, DEV-021
- **Изменения:** на странице кота показать текущий запрос, его ответственного, историю и разрешённые действия; добавить комментарий к результату.
- **Готово, когда:** участник видит прогресс; координатор может выполнить допустимый переход; каждое изменение имеет автора/дату; нельзя закрыть неактивный запрос или создать дублирующий активный запрос того же типа.

### DEV-023 — Уточнить автоматическое повторение запроса еды

- **Приоритет:** P0 · **Оценка:** 1 день · **Зависимости:** DEV-020
- **Изменения:** изменить текущее правило 24 часов так, чтобы система не показывала автоматически решённое событие как новое подтверждённое обращение без действия пользователя.
- **Готово, когда:** по истечении интервала повторный запрос можно создать вручную; история прежнего события остаётся; интерфейс объясняет доступность повторного запроса.

### DEV-024 — Согласованно обработать «дом найден»

- **Приоритет:** P0 · **Оценка:** 2–3 дня · **Зависимости:** DEV-020
- **Изменения:** определить терминальный статус случая; применять его в `GET /api/cats`, статистике, карточке, создании/закрытии помощи и поиске.
- **Готово, когда:** завершённый случай не показывается как активный на карте; карточка доступна в истории; сервер отклоняет новые запросы помощи; статистика отделяет активные случаи от завершённых.

### DEV-025 — Добавить безопасный контакт с координатором

- **Приоритет:** P0 · **Оценка:** 2–4 дня · **Зависимости:** DEV-021, DEV-030
- **Изменения:** добавить в интерфейс способ связаться с ответственным через внутреннюю форму/канал партнёра, не публикуя личный телефон или точный адрес.
- **Готово, когда:** контакт виден только в нужном контексте; в интерфейсе указано ожидаемое время ответа и что делать при срочной ситуации; отправка фиксируется или надёжно передаётся выбранному каналу.

## Этап 4. Приватность, модерация и роли

### DEV-030 — Ввести роли пользователя и серверную проверку прав

- **Приоритет:** P0 · **Оценка:** 3–5 дней · **Зависимости:** нет
- **Изменения:** добавить роль участника/координатора/модератора; определить начальное назначение роли пилотной группы; защитить соответствующие API middleware.
- **Готово, когда:** роль нельзя повысить запросом клиента; все закрытые операции защищены на сервере; ошибки доступа возвращают 403; публичные чтения остаются явно перечисленными.

### DEV-031 — Разделить точную и публичную геолокацию

- **Приоритет:** P0 · **Оценка:** 2–4 дня · **Зависимости:** DEV-012, DEV-030
- **Изменения:** определить формат точности/зоны; отдавать публичной карте приблизительную координату, а точную — только автору/назначенному координатору по правилам доступа.
- **Готово, когда:** точные координаты отсутствуют в публичных API-ответах, логах и HTML; права проверены на API; интерфейс объясняет режим видимости точки.

### DEV-032 — Добавить жалобы на запись и очередь модерации

- **Приоритет:** P0 · **Оценка:** 4–6 дней · **Зависимости:** DEV-030
- **Изменения:** добавить отправку причины жалобы (дубликат, неверное место, домашний кот, оскорбительный контент, другое), API списка и обработки жалоб, интерфейс модератора.
- **Готово, когда:** жалобу может отправить участник; решение доступно только модератору; решение и причина аудируются; модератор может пометить запись, объединить/архивировать её согласно установленным правилам.

### DEV-033 — Реализовать архивирование карточки

- **Приоритет:** P0 · **Оценка:** 1–2 дня · **Зависимости:** DEV-030, DEV-032
- **Изменения:** добавить статус/дату/причину архивации и исключить архивные карточки из обычных выдач.
- **Готово, когда:** архивирование не удаляет историю; действие ограничено правами; карточку можно найти в административной истории; связанные события помощи остаются целыми.

### DEV-034 — Добавить удаление аккаунта/запрос на удаление данных

- **Приоритет:** P1 · **Оценка:** 2–4 дня · **Зависимости:** DEV-030, DEV-035
- **Изменения:** добавить сценарий из личного кабинета и серверную процедуру удаления или обезличивания данных, учитывающую авторство публичной истории.
- **Готово, когда:** пользователь может отправить запрос; интерфейс объясняет, что будет удалено/обезличено; связанные записи не ломают ограничения БД; действие журналируется.

- **Готово, когда:** клиент не получает stack trace/SQL; все основные маршруты используют ожидаемые HTTP-статусы; интерфейс показывает полезное сообщение и сохраняет введённые данные при исправимой ошибке.

### DEV-042 — Настроить сбор ошибок и health checks

- **Приоритет:** P0 · **Оценка:** 1–3 дня · **Зависимости:** DEV-040
- **Изменения:** проверить `/health`, добавить проверку подключения к БД, структурированные серверные логи и базовый сбор ошибок деплоя без сохранения паролей, токенов и точных координат.
- **Готово, когда:** оператор может отличить недоступность API от недоступности БД; в логах есть идентификатор запроса; чувствительные поля редактируются.

### DEV-043 — Подготовить HTTPS-деплой и резервное копирование

- **Приоритет:** P0 · **Оценка:** 2–4 дня · **Зависимости:** DEV-014, DEV-042
- **Изменения:** задать целевое окружение, production переменные, HTTPS/CORS/cookie параметры и резервирование БД и фотографий.
- **Готово, когда:** приложение развёрнуто на тестовом адресе; secure cookie и CORS проверены; backup создан и успешно восстановлен по инструкции.

### DEV-044 — Подготовить экран и правила для участников пилота

- **Приоритет:** P0 · **Оценка:** 1–2 дня · **Зависимости:** DEV-025, DEV-031, DEV-032, DEV-043
- **Изменения:** добавить согласованные с пилотной организацией правила публикации, приватности, модерации, времени ответа и срочных обращений; ссылку на них в регистрации/профиле.
- **Готово, когда:** пользователь может прочесть правила до добавления данных; нет обещания мгновенной помощи; указаны контакт владельца пилота и способ сообщить о проблеме.

## Этап 6. Развитие после пилота

### DEV-050 — Добавить локальный справочник помощи

- **Приоритет:** P1 · **Оценка:** 2–4 дня · **Зависимости:** пилот
- **Функция:** каталог проверенных ветеринаров, приютов, TNR-групп и пунктов корма с территорией, контактами, источником и датой проверки.
- **Готово, когда:** у каждой записи назначен ответственный за актуализацию; есть фильтр по территории/типу; устаревшие контакты можно сообщить и исправить.

### DEV-051 — Добавить уведомления назначенным участникам

- **Приоритет:** P1 · **Оценка:** 3–5 дней · **Зависимости:** DEV-021
- **Функция:** уведомления о назначении, изменении статуса и ответе координатора; пользовательские настройки частоты/отключения.
- **Готово, когда:** нет массовой рассылки всех событий всем пользователям; уведомления не содержат точные координаты; повторная доставка не создаёт дубликаты.

### DEV-052 — Реализовать поддержку колоний/групп котов

- **Приоритет:** P2 · **Оценка:** 4–8 дней · **Зависимости:** DEV-012, пилот
- **Функция:** объединение котов в территориальную группу, общий координатор и отдельные индивидуальные медицинские случаи.
- **Готово, когда:** общий статус группы не подменяет статус отдельного кота; сценарий подтверждён пилотными пользователями; предусмотрена миграция и фильтрация на карте.

### DEV-053 — Масштабировать пилот на новые территории

- **Приоритет:** P2 · **Оценка:** 3–5 дней · **Зависимости:** DEV-030, DEV-050, DEV-051
- **Функция:** управление территориями и локальными координаторами, онбординг партнёрских групп и настройка локальных правил.
- **Готово, когда:** права координатора ограничены его территорией; новая группа может начать работу без ручного вмешательства разработчика; есть показатели качества данных по каждой территории.

## Рекомендуемый порядок реализации

1. Уже реализованы: создание кота, `DEV-001`–`DEV-003`, `DEV-010`–`DEV-011`.
2. Закрыть края пользовательского контура: `DEV-005` logout и `DEV-006` политика публичного профиля; затем `DEV-004` ошибки входа/регистрации.
3. `DEV-030` и `DEV-040`: роли и единая обработка доступа/ошибок.
4. `DEV-012` → `DEV-013` → `DEV-014`: отдельные наблюдения и фотографии; параллельно `DEV-015` актуальность данных.
5. `DEV-020` → `DEV-021` → `DEV-022` → `DEV-024`: запрос помощи от создания до результата; отдельно `DEV-023` правило повторного запроса еды.
6. `DEV-031` → `DEV-032` → `DEV-033`: точность геолокации и модерация; затем `DEV-025` контакт с координатором.
7. `DEV-041`–`DEV-044`: проверки, эксплуатация и запуск пилота.

Порядок можно скорректировать после выбора реального партнёра, но задача считается готовой к релизу только при выполнении её критериев приёмки и обновлении соответствующих типов/документации API.
